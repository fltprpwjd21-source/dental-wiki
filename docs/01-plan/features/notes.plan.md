## Executive Summary

| Perspective | Content |
|-------------|---------|
| **Problem** | 방금 만든 파일함은 "파일을 올리고 내려받는" 것만 된다. 실제로 필요한 건 상위/하위 폴더로 정리되는 트리형 메모장이고, 거기서 마크다운을 직접 쓰고 사진을 붙여 바로 볼 수 있어야 한다. (실제로 "치주과 인수인계" 폴더에 스크린샷을 올려봤지만 화면에서 바로 볼 수 없어 휴지통으로 옮긴 사용 흔적이 남아 있다) |
| **Solution** | 파일함을 트리형 노트로 확장·교체한다. 폴더를 무제한 중첩 가능하게 하고, `.md` 노트는 브라우저에서 바로 편집하며, 이미지는 올리는 즉시 화면에서 보이게 한다. 화면은 옵시디언처럼 왼쪽 트리 + 오른쪽 편집/뷰어 2단 구성. |
| **Function/UX Effect** | 왼쪽 트리에서 폴더를 펼쳐 노트를 고르면 오른쪽에서 바로 읽고 고칠 수 있고, 사진을 올리면 그 자리에서 보인다. 옵시디언과 같은 저장 형식(폴더 + md + 이미지)이라 나중에 옵시디언으로 열어봐도 그대로다. |
| **Core Value** | 인수인계처럼 "글 + 사진"이 섞인 자료를, 파일을 주고받는 방식이 아니라 한 화면에서 정리하고 바로 읽을 수 있게 한다. |

## 1. Overview

### 1.1 Purpose

진료과별 인수인계처럼 "설명 글 + 참고 사진"이 섞인 자료를, 파일을 올리고 내려받는 방식이 아니라 트리로 정리된 노트 형태로 작성·열람할 수 있게 한다.

### 1.2 Background

- 처음에는 "서버의 폴더·파일을 자유롭게 올리고 받는 기능"으로 이해해 파일함(file-server)을 만들어 배포했다.
- 실제 의도는 **옵시디언을 벤치마킹한 트리형 메모장**이었다 — 상위/하위 폴더, 브라우저에서 직접 쓰는 마크다운, 즉시 보이는 사진.
- 옵시디언 자체를 서버에서 API로 쓰는 건 불가능하다(로컬 데스크톱 앱이며 공개 서버 API가 없다). 대신 **옵시디언과 같은 저장 형식**(폴더 트리 + `.md` + 첨부 이미지)으로 직접 구현한다.

### 1.3 Related Documents

- 대체 대상: [file-server.plan.md](file-server.plan.md), [file-server.design.md](../../02-design/features/file-server.design.md)
- 기존 위키 구조: [DESIGN.md](../../../DESIGN.md) — 인증·로그·되돌리기 패턴을 그대로 재사용

## 2. Scope

### 2.1 In Scope

- [ ] 폴더 트리 (상위/하위 무제한 중첩, 펼치기/접기)
- [ ] 마크다운 노트 생성·편집·저장 (브라우저에서 직접 작성)
- [ ] 마크다운 렌더링 (제목·목록·표·코드·링크·이미지)
- [ ] 이미지 업로드 후 노트에 삽입 + 화면에서 바로 표시
- [ ] 이미지 파일 자체를 트리에서 선택하면 오른쪽에서 바로 보기
- [ ] 옵시디언식 2단 레이아웃 (왼쪽 트리, 오른쪽 편집/뷰어)
- [ ] 노트·폴더 이름으로 검색
- [ ] 노트/폴더 삭제 → 휴지통(30일) → 복구, 30일 후 자동 완전삭제
- [ ] 모든 편집·삭제 이력을 수정 불가능한 로그로 기록 (기존 file_logs 방식 유지)
- [ ] 이미 만들어진 파일함 데이터(폴더 "치주과 인수인계" 등)를 그대로 이어서 사용

### 2.2 Out of Scope

- 위키링크 `[[노트이름]]`·백링크·그래프뷰 (옵시디언의 상징적 기능이지만 이번엔 제외 — 필요해지면 별도 계획)
- 실시간 공동 편집(여러 명이 동시에 같은 노트를 타이핑) — 기존 위키처럼 낙관적 잠금으로 충돌만 감지
- 옵시디언 앱과의 양방향 자동 동기화
- 태그·즐겨찾기·정렬 커스터마이즈
- 노트 내용의 RAG 검색 편입 (위키 문서와 별개로 유지)
- 개인별 비공개 노트 (전 스탭 공유 하나의 트리)

### 3.1 Functional Requirements

| ID | Requirement | Priority | Status |

| FR-02 | 왼쪽 트리에서 폴더를 펼치고 접을 수 있다 | High | Pending |
| FR-03 | 폴더 안에 마크다운 노트를 새로 만들 수 있다 | High | Pending |
| FR-04 | 노트를 선택하면 오른쪽에 내용이 렌더링되어 보인다 | High | Pending |
| FR-05 | 노트를 브라우저에서 편집하고 저장할 수 있다 | High | Pending |
| FR-06 | 이미지를 업로드하면 그 자리에서 화면에 보인다 | High | Pending |
| FR-07 | 노트 편집 중 이미지를 삽입할 수 있다 (마크다운 이미지 문법) | High | Pending |
| FR-08 | 노트·폴더를 휴지통으로 옮기고 30일 내 복구할 수 있다 | Medium | Pending |
| FR-09 | 폴더를 지우면 그 안의 하위 폴더·노트도 함께 휴지통으로 간다 | Medium | Pending |
| FR-10 | 노트·폴더 이름으로 검색할 수 있다 | Medium | Pending |
| FR-11 | 동시에 같은 노트를 고치면 나중 저장이 앞사람 내용을 덮어쓰지 않는다 | Medium | Pending |
| FR-12 | 모든 생성·편집·삭제·복구가 로그로 남는다 | Medium | Pending |

### 3.2 Non-Functional Requirements

| Category | Criteria | Measurement Method |
|----------|----------|-------------------|
| Security | 로그인 세션 없이는 어떤 노트 API도 401 | 기존 `withSession` 재사용 + API 테스트 |
| Security | 비공개 버킷의 이미지가 로그인 없이 URL만으로 열리지 않는다 | 로그아웃 상태에서 이미지 URL 직접 호출 테스트 |
| Security | 노트 본문에 넣은 HTML/스크립트가 실행되지 않는다 (마크다운 XSS 차단) | `<script>` 삽입 테스트 |
| Performance | 트리 조회는 폴더 수가 늘어도 1회 쿼리로 처리 | 코드 리뷰 |
| UX | 좁은 화면(모바일)에서도 트리와 편집 화면을 쓸 수 있다 | 375px 뷰포트 확인 |

## 4. Success Criteria

### 4.1 Definition of Done

- [ ] FR-01~FR-12 전부 구현

## 5. Risks and Mitigation

| Risk | Impact | Likelihood | Mitigation |
|------|--------|------------|------------|
| 비공개 버킷 이미지를 화면에 띄우려다 URL이 공개로 새어나감 | High | Medium | 이미지를 인증이 걸린 서버 라우트로 중계해서 내보낸다(공개 버킷 전환 금지). 자세한 방식은 Design에서 확정 |
| 마크다운 본문에 삽입된 스크립트로 XSS | High | Medium | 렌더링 시 HTML 태그를 허용하지 않거나 sanitize 처리 |
| 폴더 트리에 순환 참조(자기 자신의 하위로 이동 등) 발생 | Medium | Low | 이동 기능은 이번 범위에서 제외하거나, 넣는다면 조상 검사로 차단 |
| 이미 배포된 파일함 데이터·화면이 깨짐 | Medium | Medium | 기존 테이블을 지우지 않고 컬럼 추가로 확장. 사용자가 만든 "치주과 인수인계" 폴더와 휴지통 항목은 그대로 보존 |
| 트리가 깊어질수록 조회가 느려짐 | Low | Low | 폴더 전체를 한 번에 읽어 클라이언트에서 트리를 조립(사내 규모에서는 수백 개 수준) |

## 7. Architecture Considerations

### 7.1 Project Level Selection

Dynamic (기존과 동일) — Next.js App Router + Supabase.

### 7.2 Key Architectural Decisions

| Decision | Options | Selected | Rationale |
|----------|---------|----------|-----------|
| 노트 본문 저장 위치 | Postgres 텍스트 컬럼 / Storage의 .md 파일 | **Design 단계에서 확정** | 편집·검색·버전관리 편의 vs 옵시디언 호환성의 맞바꿈이라 설계안 비교가 필요 |
| 트리 구조 | 인접 리스트(parent_id) / 경로 문자열 / 클로저 테이블 | 인접 리스트(parent_id) | 사내 규모에서 가장 단순하고, 전체를 한 번에 읽어 조립하면 충분 |
| 마크다운 렌더링 | 라이브러리 도입 / 직접 구현 | 라이브러리 도입 | 직접 구현은 XSS·표·코드블록 처리에서 사고가 나기 쉽다 |
| 이미지 표시 | 공개 버킷 / 인증 중계 라우트 | 인증 중계 라우트 | 병원 내부 자료라 URL만 알면 열리는 상태를 만들면 안 된다 |
| 편집 화면 | 토글 미리보기 / 좌우 분할 | 옵시디언식(왼쪽 트리 + 오른쪽 편집·뷰어) | 사용자 요청 |
